# Codex node execution — milestone 5

Agent nodes now have a **Conversation & runs** workspace. **Run node** executes the saved initial prompt through the pinned Codex TypeScript SDK on a task branch in the existing project directory. The conversation supports follow-ups, stop, retry, and an explicit fresh conversation. Activity, test output, per-attempt file diffs, and saved execution context are available in separate tabs.

New nodes use **Default Codex**: no custom profile is required. A null profile ID adds no custom role or preset profile skills; project/task instructions and explicitly selected extra skills still apply. Model/effort use configured defaults unless overridden. An explicit custom profile ID must resolve to an active item in the correct scope. Existing same-thread instructions remain in history; use New conversation to reset previous profile context.

A completed attempt means its SDK turn and configured checks settled successfully and its changes were recorded; this is distinct from workflow acceptance. [Milestone 6](workflow-scheduling.md) adds scheduling, auto/manual acceptance, human review, board progression, and explicit branch integration around this execution service. Explicit node runs now require accepted predecessors too.

Select an agent and click **Run node** in its graph details for an individual run. The same action is available in its conversation. Rerunning completed work continues its saved thread; failed attempts retry their last request. These actions, follow-ups, and new conversations execute only that node and leave other ready nodes waiting for your selection. Use **Run workflow** to enable automatic scheduling again. Canvas zoom, pan, and node placement do not require saving or block these actions.

## Task branches and code snapshots

- Every task uses a readable `codex/<todo-title>` branch in the existing project directory. Branch names get numbered suffixes for collisions and remain stable after a task rename. The app does not create a separate task folder. Each node still has an independent saved conversation.
- A run checks for unfinished Git operations and selects the task branch. Switching branches requires clean working files and index; retrying on the already-selected task branch retains local edits for the next attempt. Dirty-switch errors name the current branch and list local changes. The app never stashes, resets, or discards them. Only one code-writing node runs per project. Avoid switching branches while an agent or its checks are active; a detected branch change fails collection instead of committing onto another branch.
- A new task starts from the current branch, or the saved base branch when another managed task is selected. This keeps separate todos independent until integration. Project setup establishes an initial empty commit for new repositories. Missing saved task branches fail visibly and are not silently recreated.
- Each attempt records a complete before/after snapshot using a private index and protected `refs/constella/snapshots/<commit>` refs. Once a turn and its checks settle, including failure or stop, the app saves the resulting snapshot as a commit on the task branch and aligns its index. Files stay in the project directory, and the task branch stays selected. Acceptance remains separate from saving code.
- Users can select `main`, a task branch, or another branch in their existing IDE window while no agent is active. **Review task** shows the project directory, task/current/base branches, a copyable branch name, and an optional **Switch to task branch** action. The run command selects that branch in the project directory before starting the saved development command. Development commands are never launched automatically.
- Diffs read immutable Git objects and remain available after selecting another branch. Added, modified, deleted, and type-changed files are recorded; renames appear as delete/add. Nonignored untracked files are included. Ignored dependencies and build output stay in the same project directory. Preview limits remain 512 KB per side and 2,000 listed files; full snapshots remain in Git.

On startup, older app-managed task worktrees are migrated without touching the project checkout: their latest working files are saved to the existing task branch and their checkouts are detached, releasing the branch for normal IDE switching. The old directories remain as backups. Branch names and run snapshots remain available. Ownership, repository identity, and saved paths are checked before migration; missing or altered legacy checkouts are preserved and their tasks fail visibly until repaired. Migration is retried when reviewing or running an older task.

Integration remains an explicit human action after workflow completion. It merges the accepted task branch into its saved base branch and leaves the project directory on that branch. Archive, restart, and failed runs do not remove branches or roll back files.

If a branch change prevents saving an attempt, restore its task from Archive if necessary and open **Review task → Switch to task branch**. This explicit action can retain staged, unstaged, and untracked files when the current and saved task branches have identical committed trees. It does not commit, stash, or integrate anything. Then retry the failed node; its attempt will save progress normally. Different committed trees or unfinished Git operations remain blocked and require saving or reconciling local edits first. Starting another task does not automatically take ownership of these files.

Before starting a separate task that depends on a completed task's files (such as `project_plan.md`), integrate the prerequisite task. The workflow controls explain this before a new task starts, and node instructions require reporting explicitly required missing source files instead of inventing replacement requirements.

## Persistence and concurrency

Migration 4 appends `task_worktrees`, `node_threads`, and `node_runs`; migrations 1–3 are unchanged. Thread IDs and complete bounded attempt records are stored in SQLite, including exact node/task/project settings, resolved prompt, profile/style guide, skill text/resource hashes and archived copies, effective model/effort, predecessor summaries, prior test results, and code snapshots.

`NodeExecutionService` owns lifecycle and authorization independently of Electron. It reserves the project's single execution slot synchronously before any async work, so overlapping requests cannot create concurrent code writers in that project. Other projects can run independently. The slot stays reserved through preparation, streaming, checks, and diff collection. `GraphService` rejects active-task writes; the renderer also disables editing. Archiving through the desktop waits for the task's active attempt to stop before applying the archive command.

Named preload methods expose task state, node state, start/stop, saved attempt lookup, diff lookup, and invalidation events. No SDK, process handle, filesystem API, or credentials are exposed to the renderer. Scope and expected graph revision are checked in the service. A valid graph and active scoped assignments are required; Start, End, and Human Review nodes cannot execute SDK turns.

Each `thread.started` event persists its ID with the attempt. Follow-ups call `resumeThread` using that node's current saved ID and the same project directory. Retries preserve the last request and thread when one exists, resolving current saved configuration for the new attempt. Fresh conversations explicitly reset the current thread while retaining old attempts and code. Earlier same-thread instructions can remain in Codex's conversation history; changing a profile is not a history reset.

On startup, recorded preparing/running/testing/stopping attempts become **interrupted**. Their project changes are collected where possible and collection failures are shown. No inference, checks, or new progress commits run automatically during interrupted-attempt recovery. Dirty recovered files can be continued on their selected task branch; switching to another task still requires saving them first. Legacy-worktree migration is a separate one-time Git conversion. A storage failure retains the latest volatile attempt and shows a persistence error; additional starts are blocked until storage is restored and the app is restarted.

The UI reads the latest 20 attempts per node and retains up to 300 raw events and 500 activity items per attempt, with bounded text. All attempts remain in SQLite. Older attempts can be fetched by ID through the service; a complete history browser remains future work.

## Checks and runtime boundaries

The saved project test command is displayed before execution and runs automatically after a successful SDK turn. It runs in the verified project directory on the task branch as a local app process with the user's normal process permissions; it is separate from the SDK sandbox. Output is bounded to 64 KB. Exit failures, a two-minute timeout, and cancellation are distinct recorded outcomes. No configured command means **not run**, rather than an implied test pass. Test failures keep code changes available and feed the recorded output into the next retry/follow-up context. Stop terminates the test process group on supported platforms as well as aborting the SDK signal.

Codex uses `workspace-write`, `approvalPolicy: never`, disabled tool networking, and disabled web search. There is no automatic escalation or fabricated approval UI. Authentication, model/effort, permission, stream EOF, process, storage, and Git errors are visible in the attempt. The [integration record](codex-integration.md) documents the pinned SDK's incomplete nested tool events and lack of interactive approve/deny callbacks. Provider inference still requires account access and connectivity.

Selected skills resolve through the existing catalog service. Node runs use app-data resource archives directly so staging does not add generated skill files to code diffs. The prompt includes task and node objectives, acceptance criteria, profile/style instructions, project brief/commands, and accepted predecessor summaries supplied by the scheduler. These are context; they do not permit a model to accept a manual result or approve a review.

Every task turn also receives source-quality defaults, including when no profile is selected: respect repository formatting configuration, keep handwritten source readable, inspect edited files, and use an existing formatter when available. Explicit project/user requirements and intentional build artifacts can require a different style. These are agent instructions; the app does not automatically format source or enforce a formatting gate before acceptance.

Monaco and its worker are bundled locally and loaded on demand. The renderer permits local/blob workers but does not load a CDN or enable Node integration. The direct adapter detaches models before editor/model disposal when tabs change.

## Verification

`npm test` exercises real temporary Git repositories and SQLite with an injected SDK client: new/unborn and dirty repositories, dirty-file/index preservation and automatic progress commits, immutable snapshots, same-thread revisions, restart continuation, independent node threads, streaming item updates, project concurrency, graph freezing, stop during preparation/stream/checks, test failures/timeouts/output limits, binary/deleted/large file diffs, stale/foreign/removed assignments, missing task branches, normal IDE branch switches, legacy migration, crash recovery, and visible storage failures. These tests do not consume provider inference.

`npm run test:graph-ui` builds and opens an isolated hidden Electron fixture using the actual renderer/preload. It exercises graph edits, scope selectors, visible edges, node conversations, same-thread follow-ups, stop, test output, Monaco rendering, and tab disposal with no renderer/preload errors. `npm run build` typechecks and builds main, preload, renderer, and the local editor worker.

The live desktop checkpoint remains for the user. Official SDK guidance: [start, continue, and resume local Codex threads](https://learn.chatgpt.com/docs/codex-sdk), and [noninteractive Codex execution](https://learn.chatgpt.com/docs/non-interactive-mode).
